## 开场说明（可直接用于评审）

“我们这次做的是潘多拉工作日志与任务协作系统，服务一家公司的员工和管理者。员工使用 Android 记录每天的工作、查看公司重点和派发任务、反馈进度；管理员和上级使用 Web 在各自权限内查看工作记录、维护公司重点和跟进任务。

第一阶段要把日志收集、指令收发、四板块和日周月视图做完整。首个可演示版本先打通员工登录、写日志、提交后面板可见、管理端可见这条链路。AI 地图、MBTI、跨公司匹配、分层复核和完成率图表都暂不做。

今天主要确认范围有没有遗漏、权限是否合理、每条故事怎样验收，以及我们五个人在课程时间内能否完成。现有 27 条故事和 47 人日都是供讨论的草案，尤其工作量需要各模块负责人重新估算，不是已经承诺的工期。讨论后把通过、修改和待定项记录下来。”

## 建议的 30 分钟评审顺序

| 时间 | 主持人怎么引导 | 需要得到的结果 |
|------|----------------|----------------|
| 0–5 分钟 | 按上面的开场说明确认用户、目标和不做的内容，指出产品第一阶段包含课程 Sprint 1–3 | 共同认可项目定位和范围 |
| 5–12 分钟 | 用“员工 A 写日志，上级 L 在 Web 查看”走一遍；追问草稿、修改、其他员工能否查看 | 日志可见性和组织权限结论 |
| 12–18 分钟 | 用“L 派任务给 A，A 更新进度”和“A 向 L 请示”走一遍，再看四板块及日期视图 | 指令原文、进度、备注、邀约和汇总规则结论 |
| 18–25 分钟 | 按 backlog 请 Android、Web、后端和测试相关成员说出工作量及依赖；确认现有技术方案 | 逐项估算、Sprint 容量、负责人；不能只认可总数 |
| 25–30 分钟 | 逐条读回“通过/修改/待定”，明确服务器、月相样例和规格同步由谁处理、何时完成 | 可执行的结论和待办；记录实际参加人及证据 |

评审不需要当场写代码。每个有争议的点至少记录一个决定；暂时不能决定的内容要有跟进人和时间，不能默认等同于通过。

建议产品负责人、Android、Web、后端、测试相关成员共同参加；成员姓名、开会时间和主持人尚未填写，不预设出席情况。

| 议题 | 当前建议/待确认内容 | 会后需要记录 |
|------|--------------------|--------------|
| 用户、痛点与范围 | 单公司内部协作；Sprint 1 最小闭环，Sprint 2 补齐第一阶段；AI/MBTI/跨公司/分层复核/统计图延期 | 是否认可；需要删减或调整的故事 ID |
| 日志 | 本人草稿和已提交日志均可编辑；草稿仅自己可见；已提交修改后管理端刷新可见 | 草稿隐私、补记历史日期、多条日志及 5000 字符上限是否认可 |
| 角色与组织 | 三档角色 + 直属上级组织树；上级只读下属已提交日志，管理员不代写个人日志 | 组织范围、创始人映射及“先转移下属再降为员工”的规则是否认可 |
| 四板块 | 上方原文只读可加个人备注；下方本人可改；派发列表排序和个人十大事生成规则见 §4.2 | 最大数量、排序、手改保留与汇总周期 |
| 指令与邀约 | 责任人更新进度不等于修改原文；邀约接受转一条正式派发，拒绝须回复 | 身份重叠时原文/进度分权、状态转移和异常处理是否认可 |
| 估算与容量 | 功能 P0 初估 43 人日、P1 1 人日，非功能专项 3 人日，共 47 人日；共享能力不重复计入 | 每个成员可投入时数、每条故事重估、Sprint 内容量与依赖 |
| 技术选型 | 沿用 Spring Boot 3 / Java 17 / MySQL 8 / Kotlin Compose / Vue 3 / Docker Compose / GitHub Actions | 明确同意或调整项，不将方案草稿写成已通过 |
| 服务器 | 后端确认云厂商、账号归属、费用、域名、代理方案；尚未购买或部署 | 负责人、预算、费用承担及完成日期 |
| 非功能验收 | 月相主题、401/403 必测；固定日期样例需独立来源，明确跨日切换；异常不丢输入 | 测试数据、预期结果、运行环境、证据负责人 |
| 同步与验收 | 先同步规格与接口再实现，按产品文档 §5.3 演示两条闭环 | 规格变更负责人、关联 PR/Issue、复查人 |
