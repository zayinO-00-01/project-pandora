# 四级角色与直属上级查看申请

在 22 号恢复版及月历、双主题背景上增加角色入口，保留统一视觉风格。

| 角色 | 总览标题与入口 | 查看范围 |
| --- | --- | --- |
| 员工 STAFF | 我的工作 / 查看上级 | 自己；查看直属上级需申请 |
| 团队长 TEAM_LEAD | 团队总览 / 团队成员 | 团队下属；查看直属上级需申请 |
| 部门老总 DEPT_HEAD | 部门总览 / 部门成员 | 沿组织关系穿透部门下属；查看直属上级需申请 |
| 创始人 FOUNDER | 公司总览 / 公司组织 | 沿公司组织关系向下穿透 |

层级高不自动开放其他部门。所有向下查看均以实际 manager_id 组织关系为依据；ADMIN 继续使用 Web。旧 LEADER 保留直属下属范围。

用户确认向上申请仅可选择直属上级。下级填写理由，上级在“查看申请”批准或拒绝；批准后可查看该上级已提交日志与任务进展，不能编辑。授权持续至上级撤销，组织关系或角色变化使关系条件不再满足时，服务器立即拒绝继续读取。待审批、拒绝、撤销均不开放内容。任何角色查看他人日志都不返回草稿。

总览入口进入组织页：领导默认下级工作，员工默认直属上级。领导按角色分组查看授权范围内成员，打开成员工作后是独立只读页面。申请页只显示本人参与的申请，审批与撤销仅允许被查看的直属上级执行。申请理由最长 500 字；每对上下级保留一条状态记录，拒绝或撤销后可重新申请；并发审批用版本与数据库唯一约束防止重复/覆盖。

## 接口与升级

- GET /api/v1/users/organization：授权下属公开身份及直属上级身份，不含密码或日志。
- GET /api/v1/logs?userId=ID、GET /api/v1/tasks?userId=ID：服务端执行关系与批准状态校验。
- GET /api/v1/view-requests：本人参与的申请。
- POST /api/v1/view-requests：targetId、reason，仅直属上级。
- PUT /api/v1/view-requests/ID：status 为 approved、denied 或 revoked。

APK 与后端需要同时更新，旧服务没有组织/申请接口时，页面明确显示尚未开放，不模拟批准或成功。新后端通过 Flyway V4 新增 view_requests 表，不修改既有账号角色与上下级数据。四种账号及正确组织关系仍由管理员维护；不能仅靠前端角色扩大权限。现有默认演示账号仍保留 ADMIN、LEADER、STAFF。
