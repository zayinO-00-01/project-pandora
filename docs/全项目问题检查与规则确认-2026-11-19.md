## 问题详情与后续验收建议

### BUG-01：MySQL首次部署被头像字段迁移阻断

- **触发条件**：全新MySQL数据库按仓库迁移顺序升级，例如使用当前Docker Compose配置启动。
- **原因与影响**：V12定义 `avatar_image VARCHAR(200000)`，超过MySQL的VARCHAR长度上限。Flyway执行失败后，API不能正常启动。H2接受该定义，因此H2测试不能证明MySQL部署可用；此结论不表示现有H2云端服务已经故障。
- **代码依据**：[V12__user_avatar_image.sql](../backend/src/main/resources/db/migration-h2/V12__user_avatar_image.sql)，第1行；[docker-compose.yml](../docker-compose.yml)，第31行启用MySQL配置。
- **建议与验收**：选择兼容的文本类型并核对实体映射，在空MySQL库及升级副本验证全部迁移与启动。实施前需考虑已执行迁移的校验值，不能直接改历史脚本后对现有库全量repair或删库。

### BUG-02：打开任务修改会覆盖保留的任务草稿

- **触发步骤**：新建任务并填写内容 → 点击“返回任务工作台 · 保留输入” → 打开已有任务并点击“修改任务”。修改已有任务后返回，再次点击该任务的修改入口，也存在相同风险。
- **原因与影响**：`editTaskDetails()`无条件从服务器任务创建新缓冲，并写入同账号唯一的任务草稿槽，直接覆盖原输入，没有放弃确认。
- **代码依据**：[PandoraViewModel.kt](../android/app/src/main/java/com/projectpandora/app/PandoraViewModel.kt)，第403—410行；[TaskScreen.kt](../android/app/src/main/java/com/projectpandora/app/ui/TaskScreen.kt)，第228行承诺保留输入。
- **建议与验收**：再次编辑同一任务时恢复原草稿；打开其他任务时明确处理已有草稿。验证新建、编辑、返回、重登后均不会无提示丢失内容。

### BUG-03：日志草稿恢复期间，返回可能直接删除输入

- **触发步骤**：编辑一篇创建未满24小时的已有日志，留下本机修改 → 重启或重新登录 → 原日志列表加载缓慢或失败 → 点击返回。
- **原因与影响**：登录先恢复编辑缓冲，再异步读取日志。`logEditorReadOnly()`把“尚未找到原日志”直接判为只读，界面误称已超过24小时；只读页返回又直接执行`discardEditor()`，删除本机缓冲，不出现放弃确认。
- **代码依据**：[WorkspaceRules.kt](../android/app/src/main/java/com/projectpandora/app/data/WorkspaceRules.kt)，第20—21行；[LogScreens.kt](../android/app/src/main/java/com/projectpandora/app/ui/LogScreens.kt)，第115—117、136行；[PandoraViewModel.kt](../android/app/src/main/java/com/projectpandora/app/PandoraViewModel.kt)，第318—323、912—915行。
- **建议与验收**：区分加载中、读取失败和确实过期；无法确认状态时保留输入。验证断网恢复、慢网立即返回和实际超时三种场景。

### BUG-04：并发保存可能把已提交日志退回草稿

- **触发顺序**：A设备的保存草稿请求先读取`draft` → B设备提交同一日志并完成事务 → A设备随后写回旧状态。
- **原因与影响**：更新和提交没有共同的行锁或版本检查，状态校验仅基于请求读到的旧对象，A可能将状态写回`draft`。两端都可能显示成功，已提交日志又从领导视图消失，违反“已提交不能退回草稿”的规则。
- **代码依据**：[WorkLogController.java](../backend/src/main/java/com/projectpandora/api/log/WorkLogController.java)，第52—70行；[WorkLogEntity.java](../backend/src/main/java/com/projectpandora/api/log/WorkLogEntity.java)没有版本字段。
- **建议与验收**：保护状态检查与写入的一致性。通过可控并发交错验证提交后的状态不可被旧草稿请求回退，正文也不被旧对象覆盖。

### BUG-05：每日事项多设备更新会静默覆盖修改

- **触发步骤**：两台设备先加载同一事项 → A修改标题或拖动日期 → B仍使用旧内容勾选完成。
- **原因与影响**：勾选操作复制整条旧事项提交，后端全量更新标题、日期和完成状态，没有冲突检查，A的修改会被恢复成旧值。
- **代码依据**：[DailyTodos.kt](../android/app/src/main/java/com/projectpandora/app/ui/DailyTodos.kt)，第116行；[PersonalTodoController.java](../backend/src/main/java/com/projectpandora/api/todo/PersonalTodoController.java)，第36行。
- **已确认规则**：不同字段的修改分别保留；同一字段发生冲突时展示最新内容和本次修改，保留输入，由用户决定采用最新版还是确认提交自己的修改。
- **后续验收**：至少覆盖改标题与勾选、改日期与勾选、双方改标题、冲突后取消及确认提交；确认提交也需基于最新状态，避免再次无提示覆盖。

### BUG-06：每日事项新建超时后重试可能重复创建

- **触发条件**：首次新建请求已在服务器保存，但响应丢失或读取超时；用户在保留的新建窗口再次点击保存。
- **原因与影响**：重试仍发送POST，后端每次生成新UUID，不识别是否是同一次创建。第二次请求会创建相同事项，第一条可能直到刷新后才出现。
- **代码依据**：[DailyTodos.kt](../android/app/src/main/java/com/projectpandora/app/ui/DailyTodos.kt)，第67—74、127行；[PersonalTodoController.java](../backend/src/main/java/com/projectpandora/api/todo/PersonalTodoController.java)，第35行。
- **建议与验收**：让同一次创建的重试可被识别并返回原结果，不按标题去重，以免阻止用户有意创建相同事项。模拟服务器已提交但响应中断，重复保存后仅产生一条记录。

### BUG-07：Docker部署缺少Web管理端构建与打包

- **触发条件**：全新检出源码后走Docker Compose部署，或启用当前同样只调用Compose的部署工作流。
- **原因与影响**：构建上下文只有`backend`，Dockerfile只执行Maven；仓库没有跟踪已构建的Web静态文件，POM也未配置前端构建。即使数据库迁移成功，镜像仍缺少Web管理页面。本地`Start-Demo.ps1`预先复制静态资源的流程会掩盖这一问题。
- **代码依据**：[Dockerfile](../backend/Dockerfile)，第5—7行；[docker-compose.yml](../docker-compose.yml)，第24行；[deploy.yml](../.github/workflows/deploy.yml)。
- **建议与验收**：将Web构建纳入部署产物流程。使用干净源码目录构建，确认无需本机预先生成静态文件，首页、静态资源、管理员登录和业务API均可用。

### BUG-08：缺少开始时间的旧任务允许拖动却无法改期

- **触发步骤**：对历史遗留、`startAt`为空且有截止时间的有效任务长按拖动到另一日期。
- **原因与影响**：V20新增可空开始时间但未回填历史任务；前端仍允许拖动，并原样提交空开始时间，后端必填校验返回“请选择开始时间”。
- **代码依据**：[PandoraViewModel.kt](../android/app/src/main/java/com/projectpandora/app/PandoraViewModel.kt)，第396、1069—1072行；[CreateTaskRequest.java](../backend/src/main/java/com/projectpandora/api/task/CreateTaskRequest.java)，第14行；[V20__task_start_at.sql](../backend/src/main/resources/db/migration/V20__task_start_at.sql)。
- **已确认规则与验收**：拖动时先弹窗补充开始时间，再提交改期，不自动编造时间。取消弹窗不得改期；保存后仍遵守原权限和审批流程。

### BUG-09：逾期任务仅修改标题或说明也被拒绝

- **触发步骤**：已有任务开始、截止时间完整，但截止日期为昨天或更早；只改标题、说明或优先级，保持原时间提交。
- **原因与影响**：编辑入口复用新建日期校验，因旧截止日期早于今天而拒绝保存。现有文档对新建与编辑的限制口径曾有差异，本次已由用户明确规则。
- **代码依据**：[TaskService.java](../backend/src/main/java/com/projectpandora/api/task/TaskService.java)，第137—138、190—191行。
- **已确认规则与验收**：允许逾期任务修改文字等内容，保留原截止时间；主动调整时间时再校验新的时间范围。验证普通成员与创始人编辑、保持时间与主动改期，并保留原审批要求。

### BUG-10：管理员清空出生、入职日期不生效

- **触发步骤**：打开已有出生日期或入职日期的账号 → 清空日期输入框 → 保存。
- **原因与影响**：前端明确发送对应字段为`null`，后端仅在非空时调用setter，导致保存显示成功但旧日期保留，错误资料无法清除。
- **代码依据**：[admin-state.js](../web/src/admin-state.js)，第32—37行；[AdminUserController.java](../backend/src/main/java/com/projectpandora/api/admin/AdminUserController.java)，第123、125行。
- **建议与验收**：明确区分“未传字段保持原值”和“显式清空”。验证两种日期分别清空、同时清空，以及只改其他资料时原日期不被误删。

### BUG-11：并发发布或启用可能突破公司事项十条上限

- **触发条件**：当前已有9条启用事项，两位管理员同时新增启用事项，或同时启用两条不同的停用事项。
- **原因与影响**：两个事务都可能读取到计数9并通过检查，提交后出现11条。普通事务注解并不会自动将独立事务的“计数后写入”串行化。
- **代码依据**：[CompanyNoticeService.java](../backend/src/main/java/com/projectpandora/api/notice/CompanyNoticeService.java)，第44、71行。
- **建议与验收**：让新增和启用共用可靠的原子限额控制。并发验证新增、新增与启用、两个启用的组合，启用总数始终不超过10，失败请求明确提示。

### BUG-12：有权查看的任务多标签缺失，部分标签保存被拒绝

- **触发步骤**：组长给员工创建带多标签的任务，由部门负责人进入初审详情；或创始人进入本人未创建、未负责的任务详情修改标签。
- **原因与影响**：标签接口把任务范围限定为本人创建或负责，未覆盖下属查看和临时审批详情。任务详情接口仅提供旧单标签，无法补回完整集合，因此审批人可能完全看不到多标签。保存接口又复用该范围，在检查创始人权限之前就可能返回403。下属日志标签集合的读取也存在相同范围不一致。
- **代码依据**：[ContentLabelsController.java](../backend/src/main/java/com/projectpandora/api/label/ContentLabelsController.java)，第19—28行；[TaskResponse.java](../backend/src/main/java/com/projectpandora/api/task/TaskResponse.java)，第11行；[WorkLabels.kt](../android/app/src/main/java/com/projectpandora/app/ui/WorkLabels.kt)，第40行。
- **建议与验收**：分别定义读取和修改范围，读取与对应内容权限一致；创始人修改按已确认权限执行，不能因此扩大普通成员权限。验证创建初审、变更审核、下属内容、普通详情及权限撤销后的访问。

### BUG-13：App与Web电话格式规则不一致

- **触发步骤**：本人在App保存`010-12345678`等座机号码；管理员随后在Web编辑该账号，即使只修改角色、停用状态或密码，也会被手机号格式校验拦截。
- **原因与影响**：两端共用同一个`phone`字段，App允许一般联系电话，Web和管理员接口只接受有效的11位大陆手机号。
- **代码依据**：[UserController.java](../backend/src/main/java/com/projectpandora/api/user/UserController.java)，第44、57—60行；[admin-state.js](../web/src/admin-state.js)，第27—30行；[App.vue](../web/src/App.vue)，第215—216行。
- **用户决定**：本项暂缓，电话字段、格式和唯一性规则维持现状。不得把此前提出的“统一联系电话、允许重复办公号码”建议写成已采纳方案。

## 已确认的产品规则

下表是本次讨论结果，不表示相应代码均已完成实现。

| 事项 | 用户确认结果 |
| --- | --- |
| 任务标签 | 属于分类信息，可以独立修改，无需审批；后续需统一独立标签入口与任务编辑中的标签处理口径 |
| 日志超过24小时 | 正文和日期继续受原规则约束，保留本人通过独立标签入口重新分类的能力 |
| 旧任务缺少开始时间 | 拖动改期前要求补充开始时间，取消则不提交，不自动生成业务时间 |
| 每日事项多设备修改 | 不同字段分别保留；同一字段冲突时展示双方内容、保留输入，由用户决定采用最新版或确认自己的修改 |
| 电话规则 | 暂不调整，维持现状 |
| 逾期任务编辑 | 允许只修改标题、说明等并保留原截止时间；主动调整时间时校验新范围 |
| 当前工作边界 | 只检查、讨论和整理文档；尚未实施修复或发布 |

## 补充观察与未验证项

### 次要问题：连续查看通知可能漏标已读

慢网下查看A通知后立即返回，再查看B通知；若A的已读请求尚未完成，第二次请求会因`notificationReadBusy`直接返回，没有排队。B可能仍保持未读，且没有相应重试提示。

依据：[PandoraViewModel.kt](../android/app/src/main/java/com/projectpandora/app/PandoraViewModel.kt)，第858—872行；[InboxScreen.kt](../android/app/src/main/java/com/projectpandora/app/ui/InboxScreen.kt)的“查看详情”按钮未受该忙碌状态限制。该项为较轻的补充问题，未计入上表13项，尚待慢网验证。

### 需要设备验证的手势疑点

- 日历尺寸拖动过程中被系统取消或切到后台，返回后是否正确恢复滚动和吸附状态。
- 日历仍在尺寸吸附动画时长按拖动任务，浮层位置和目标日期高亮是否持续跟随手指。

这两项只有检查建议，没有足够证据判为已确认缺陷。已核对的周视图跨月日期补齐、静态拖动坐标换算未发现确定错误。

### 未发现的问题与文档偏差

- 已核对的任务拖动改期路径会保留原单标签和多标签，不能记为“拖动必然丢标签”。
- 独立修改任务标签、超过24小时修改日志标签已获用户认可，不能继续作为审批绕过或时间限制绕过上报。
- 发布记录仍停在0.10.6，而源码已到0.10.9；部分旧文档仍写开始时间选填。需要后续同步，但本轮没有核验云端实际版本，不能据此断言最新源码已经或尚未上线。
