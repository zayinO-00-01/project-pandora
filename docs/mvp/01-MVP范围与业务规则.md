# MVP 范围与业务规则

## 产品目标与反馈问题

首轮解决两个问题：员工能否方便地记录一天的工作；管理者能否快速找到指定员工、指定日期的工作记录。

甲方现场操作：员工用手机浏览器登录 → 新建日志并保存 → 上级用电脑浏览器刷新查询 → 员工修改 → 上级刷新看到修改。数据必须来自后端和 MySQL，重新登录后仍可查询。

“即时反馈”指尽早让甲方使用并提出意见。首轮不引入 WebSocket 或自动实时推送；保存后刷新可见即可验证需求。

## 方案比较与选择

| 方案 | 获得的反馈 | 成本与限制 | 本轮安排 |
|---|---|---|---|
| Android 日志 + Web 查看 + 真实后端 | 操作方式、字段、权限、双端一致性 | 需要 Android 构建、安装与双端联调 | 后续接入，满足最终课程要求 |
| 响应式 Web 同时提供员工和领导入口 | 更快通过链接试用 | 最终仍需补 Android，网页个人入口可继续保留 | 用户已选择，本轮采用 |
| 点击原型或静态假数据 | 页面和布局意见 | 不能验证保存、权限和数据持久化 | 仅用于开发前沟通，不算可运行 MVP |

## 首轮范围

| 能力 | 最小实现 | 验收结果 |
|---|---|---|
| 登录 | 预置账号、用户名密码登录、退出 | 正确身份进入；错误口令不发 token |
| 员工记录 | 日期、正文、新建、保存、修改 | 真实落库，列表和详情能重新读到 |
| 个人查询 | 按单日查询、分页列表、详情 | 仅自己的数据 |
| 领导查询 | 直属下属选择、按单日查询、详情 | 只能读取当前直属下属数据 |
| 基础反馈 | 加载中、空列表、失败重试、输入保留 | 不把保存失败显示为成功 |
| 演示准备 | 演示账号、测试数据、运行说明、反馈表 | 甲方能亲自完成主流程 |

首轮不做注册、角色编辑界面、密码找回、日志删除、附件、审批、任务派发、四板块、完整日周月视图、统计分析。完整产品仍保留原核心用户故事；这些功能按反馈安排后续增量，不全部挤入首次交付。

## 首轮页面

仅一个 Vue 工程：`/login` 登录；`/my/logs` 本人列表及日期筛选；`/my/logs/new` 新建；`/my/logs/:id` 本人详情；`/my/logs/:id/edit` 编辑；`/team/logs` 领导查询。团队列表可用抽屉读取详情，复用只读展示组件。领导也可写本人日志；员工不显示团队入口，后端仍独立鉴权。

按 360px、390px 手机宽度和 1366px 桌面宽度检查。手机列表用卡片，筛选控件允许换行，正文和按钮不横向溢出；使用普通响应式页面，首轮不做 PWA 安装或离线模式。

## 业务规则

1. 一名用户同一天可以有多条日志；不是“一人一天只能填一次”。列表默认当天，可切换单日；不传日期表示全部历史。
2. 日志日期采用 `Asia/Shanghai` 的业务日期，可填当天或过去日期，禁止未来日期。
3. 正文去除首尾空白后为 1–2000 个 Unicode 码点；纯空白拒绝。保存纯文本，客户端不按 HTML 执行。前后端按同一口径计数。
4. 作者由登录身份确定，创建/修改请求不得提供或变更 `userId`。姓名由用户资料返回。
5. 保存成功即对授权上级可见，作者仍可修改。首轮无 `draft/submitted/archived` 状态，无提交按钮。
6. `users.manager_id` 表示直属上级。首轮仅支持直属范围；不递归查询、不支持跨公司。
7. 所有有效用户可读写本人日志；仅 `LEADER` 可读取其直属下属日志。上级对下属日志只读。`ADMIN` 首轮没有全员日志查看特权，系统维护能力后续单独定义。
8. 权限依据数据库中的当前角色、关系判断。账号关系改变后，下一次请求即使用新范围。首轮不开放关系编辑 API。
9. 修改使用版本号。若他处已修改，返回 409，保留本地输入，提示重新读取后手动处理；不静默覆盖。
10. 首轮不自动重试写请求。保存期间禁用重复点击；超时属于结果不确定，保留正文并提示先刷新列表核对，避免自动重复创建。

## 甲方反馈与下一轮决策

首次演示重点询问：现有日志字段够不够、同日多条是否合适、领导的筛选方式是否方便、保存后即对直属上级可见是否符合工作习惯。

记录字段：反馈编号、演示版本/提交、操作场景、甲方原话、观察结果、处理决定、关联故事/change、负责人、验证时间。不得将未收到的意见记录为甲方已确认。

每次演示后区分：阻断使用的缺陷立即修复；对当前目标必要的改进排入下一增量；新模块进入 Backlog 后评估。不要现场承诺把所有建议都加进正在开发的版本。
