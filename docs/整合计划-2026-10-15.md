## 已确认方向

- 沿用 main 的五角色：ADMIN 只在 Web 管理账号；FOUNDER / DEPT_HEAD / TEAM_LEAD / STAFF 在 Android 办理业务。关闭公开注册，管理员维护账号、角色、上下级与停用状态。
- 用户本次明确采用 yukino 两条规则：日志仅可写七天前至今天；允许申请查看直属上级，经被查看者审批后只读，支持拒绝/撤销。
- 保留 yukino 当前 Android 视觉、月历、浅深主题、日志与任务反馈等成果。本轮优先打通真实业务；公司/个人十大事、个人备注和资料编辑等待后续。

## 实施顺序

### 1. 固定基线与数据库升级

以最新main后端为基础，整合zayin日志/任务实现与yukino必需增量。先保存现有合并现场，再整理专用整合分支，避免将未完成冲突直接推上远程。角色V3以main已发布版本为准，任务与查看申请安排后续唯一版本；针对已有main库及旧zayin库分别设计升级路径。已应用过的迁移不能直接改名后要求用户删除数据库；旧库升级前备份，校验历史日志/任务保留。新装库也必须能首次启动。

涉及：backend/src/main/resources/db/migration、角色/账号/登录/JWT代码、必要本地升级工具及说明。

### 2. 统一角色权限与日期规则

- ADMIN不可读写日志、面板、任务、业务组织或查看申请；仅管理账号。
- STAFF本人；TEAM_LEAD/DEPT_HEAD按实际manager_id向下；FOUNDER按main全公司业务范围。停用账号不能登录，旧token也不能继续使用；业务列表不包含停用/管理员账号。
- 业务领导可向授权下级派发；只有责任人可反馈进度。向上只读授权不授予派发、编辑或更新进度权限。
- 上海时区today-7至today两端包含，共8个日期；历史读取不设期限。修改需同时检查原日期和目标日期，超期记录不能通过改成今天绕过；已提交保持同ID与提交状态。

涉及：AccessService、UserController、WorkLogController、TaskService、JwtAuthFilter，保留main管理员账号接口。

### 3. 完整接入直属上级查看申请

复用yukino `/users/organization`、`/view-requests` 与按userId读日志/任务契约。只有直属上级身份可申请，只有被查看者能审批；授权仅只读且不含草稿；撤销立即生效。对停用、组织变更、角色变更、并发审批重新校验；账号管理防组织环/错误上级，避免权限通过数据配置被绕过。

涉及：ViewRequest模块/迁移、组织API、权限代码；Android现有OrganizationScreen主要做兼容与真实联调，不重做视觉。

### 4. 补两端缺失入口

- Web：ADMIN登录、GET/POST /admin/users、PATCH /admin/users/{id}，支持列表、新建、修改角色/上下级、停用/启用；业务账号提示改用App，移除旧领导业务工作台作为当前主入口。
- Android：保留当前页面；真实登录/恢复接新五角色；补任务创建提交及责任人选择，继续真实进度反馈；组织/申请与日期限制配新后端联调。
- 会话失效和保存失败保留同服务同账号输入，不显示虚构成功。

### 5. 少量关键验证与交付

仅跑必要的后端权限/七天边界/审批撤销/数据库升级用例、Android契约及构建、Web生产构建。全部通过后做一次真实流程：管理员建账号设链 → 员工写日志 → 上级App查看/派发 → 员工反馈 → 直属查看申请批准/撤销。无新失败不反复跑整套测试，手机UI/网络体验可交用户。

同步OpenAPI、OpenSpec与一份当前启动/账号/演示说明；生成可安装APK。最终要能让组员从干净源码启动，而非依赖旧机器的数据库、产物或密钥。当前用户已授权将此版本推送到 `zayin`；不直接合并 `main`。

## 暂不扩展

公司/个人十大事、备注和资料编辑、完整任务请示邀约、其他日历形式、月相主题及云部署按后续优先级推进；“查看上级的申请”与“向上请示/邀约任务”是两个不同功能。
