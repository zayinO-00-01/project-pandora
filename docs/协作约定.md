# 协作约定

> 适用于 Project Pandora 五人小队。  
> 过程考核证据：Git 提交与分支、Pull Request 审阅、Issue、**飞书多维表格/CodeArts 看板**、OpenSpec、每周周报。

## 1. 工具分工（不要混用）

课程要求 Git 协作与项目管理看板**同时**存在，不能互相替代。

| 用途 | 工具 | 说明 |
|------|------|------|
| 代码、分支、PR、缺陷与过程讨论 | GitHub `zayinO-00-01/project-pandora` | 结题需截图：分支、Network、Contributors、Issue，并备注各 ID 对应哪位成员 |
| 项目管理看板 | **飞书多维表格**（或 CodeArts，二选一，组内只选一个） | 课程指定工具。卡片必须能对应到 **Sprint** 与 **OpenSpec 的 change/task**。结题导出 Excel |
| 规格与变更 | `openspec/` | proposal → specs → design → tasks；相关 AI 工作流文件一并进版本库 |
| 周报与纪要 | 飞书周报模板 + `docs/周报/`、`docs/会议纪要/` | 周五课上汇报；仓库留一份，便于追溯 |

飞书模板：

- 项目管理：[基本模板](https://www.feishu.cn/base/JUGHbxfnDaj32nsfZMrcw71onOg)
- 团队周报：[周报模板](https://www.feishu.cn/docx/ZAOudhvkAorS1jxhABHcll2lnbg)

**GitHub Projects 不能代替飞书/CodeArts。** Issue 仍要开，用来挂 PR、记缺陷和过程证据。

## 2. 仓库与个人贡献

全体成员对产品质量共同负责，同时必须留下**可核验的个人贡献**（评分会按 Git、看板、OpenSpec tasks、PR、周报调整个人分）。

- Owner 将另外 4 人加为 Collaborator（Write）
- 每人只用本人 GitHub 账号提交，禁止共用账号
- 对照表维护在 [团队分工.md](./团队分工.md)（姓名 ↔ GitHub ID）
- 可核验来源：本人 commit、本人发起的 PR、Issue Assignee、看板负责人、周报中的个人完成项
- 结题每人写 200 字以内：自己负责的**开发**和**测试**各是什么

## 3. 分支与 Pull Request

| 分支 | 用途 |
|------|------|
| `main` | 可演示基线；仅通过 PR 合并 |
| `feature/<模块>-<简述>` | 功能，如 `feature/android-log-create` |
| `fix/<简述>` | 缺陷修复 |
| `docs/<简述>` | 文档或 OpenSpec |

- `main` 开启分支保护：必须 PR，至少 **1 位非作者** Approve
- 紧急修复可先合并，但事后补 PR 说明与审阅记录
- 审阅意见和修改必须留在 GitHub，不要只在微信里改完
- 一个 PR 对应一个 Issue，并写明 OpenSpec change（如有）
- PR 描述包含：改了什么、关联 Issue/change、如何自测、结果
- 优先 Squash and merge

## 4. Issue、Backlog 与看板

- 功能、缺陷、文档任务都建 GitHub Issue，并打 Sprint 标签（`sprint-0` … `sprint-3`）
- 同一事项在飞书看板上有一张卡片，字段至少包括：Sprint、OpenSpec change、task 编号、负责人、状态、优先级、工作量估算
- 认领后再改代码（GitHub Assignee = 看板负责人）
- 需求待办以 [backlog.md](./backlog.md) 为仓库内索引，与飞书表保持一致
- 每个 Sprint 开始时：把上一 Sprint 未完成的故事挪过来；新需求先改 Backlog 和 OpenSpec，再写代码
- Sprint 2 起可以根据前序经验**重新估算**优先级和工作量，改动记在 Backlog 修订说明里

### 缺陷 Issue 必填

现象、复现条件、优先级、处理状态、关联提交或 OpenSpec change。模板见 `.github/ISSUE_TEMPLATE/bug.md`。

## 5. OpenSpec 与需求变更

- 新能力或行为变更：先建 `openspec/changes/<change-id>/` 的 proposal、specs、design、tasks
- **禁止**只改代码。需求或接口一变，必须**同时**更新：飞书看板 + OpenSpec change（以及受影响的产品文档）
- tasks 勾选完成 ≠ 功能合格，必须有运行或验收证据（测试记录、截图或 CI）
- 完成后把 delta 合并进 `openspec/specs/`，change 移到 `openspec/changes/archive/`，保证当前规格与产品一致
- 规格里每个核心能力至少有正常场景，以及必要的异常/边界场景

## 6. 开发、测试与每 Sprint 增量

五人全员开发。测试从 Sprint 1 就做，Sprint 3 是集中验证和补证据，不是第一次测试。每个 Sprint 结束时必须有一个**可演示、可运行**的产品增量（Sprint 0 的增量是工程基线与文档，从 Sprint 1 起必须能点开主路径）。

每人负责自己模块：

- 正向验收
- 至少一个异常或无效输入
- PR 里写明冒烟结果

另外：

- 核心业务逻辑有单元测试，覆盖正常、边界、异常输入（后端主责）
- 至少 1 条核心链路做集成或系统测试（登录 → 写日志 → 数据层可查 → 另一端可见）
- 已选的两项非功能需求都要有证据（见团队分工：月相主题、鉴权）
- 测试报告放 `docs/测试/`，随 Sprint 累积，不要拖到结题再补

## 7. 周报、汇报与甲方沟通

- **每周五**课上简短进展汇报，并产出周报：已完成、下一步、存在问题
- 仓库文件：`docs/周报/YYYY-MM-DD-第N周.md`（与飞书周报内容一致）
- **每周三前**可约甲方（任课教师）一次，限时 15 分钟
- 技术选型、范围裁剪、接口变更写入 `docs/会议纪要/`

## 8. 目录边界

| 目录 | 主要修改人 |
|------|------------|
| `backend/` | 后端主责 |
| `android/` | Android 主责（两人不同包路径） |
| `web/` | Web 主责 |
| `openspec/`、`docs/` | 过程协调人牵头，全员改自己相关部分 |

跨模块先在 Issue 里对齐接口字段，再并行开发。

## 9. 提交信息

```
feat(android): 完成日志新建页
fix(backend): 修复任务派发权限校验
docs(openspec): 补充日志规格场景
test(backend): 增加日志创建边界单测
```

## 10. 运行与流水线

技术选型、服务器和 CI/CD 以产品文档第 3.1 节为准。开发开始后不要改这几条：同一份 Docker Compose、配置外置、接口前缀不写死、Flyway 管表、CI 不连云数据库。

微服务拆分仍然不做。公网服务器和 GitHub Actions 本组已经决定要做。
