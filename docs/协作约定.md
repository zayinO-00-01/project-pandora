# 协作约定

> 适用于 Project Pandora 五人小队。过程考核证据：提交历史、分支、PR、Issue、看板、OpenSpec。

## 1. 仓库与权限

- 远程仓库：https://github.com/zayinO-00-01/project-pandora
- 仓库 Owner 须将另外 4 名成员添加为 **Collaborator**（Settings → Collaborators）
- 每人使用本人 GitHub 账号提交；禁止共用账号
- 在 [团队分工.md](./团队分工.md) 维护「姓名 ↔ GitHub ID」对照表

## 2. 分支策略

| 分支 | 用途 |
|------|------|
| `main` | 可演示、可运行基线；仅通过 PR 合并 |
| `feature/<模块>-<简述>` | 功能开发，例如 `feature/android-log-create` |
| `fix/<简述>` | 缺陷修复 |
| `docs/<简述>` | 仅文档/OpenSpec |

规则：

- 禁止直接向 `main` push（Owner 请在 GitHub 打开 branch protection）
- 一个 PR 尽量对应一个 OpenSpec change 或一个 Issue
- 本地开发前先 `git pull origin main`，再切功能分支

## 3. Pull Request

- 除紧急热修外，合并前至少 **1 位非作者** Review 并 Approve
- PR 描述须包含：改动说明、关联 Issue/OpenSpec change、如何自测
- Review 意见与修改保留在 GitHub 讨论中，勿私下改完不留痕
- 合并方式优先 **Squash and merge**（保持 main 历史清晰）

## 4. Issue 与看板

- 功能/缺陷/文档任务一律建 Issue，并打上 Sprint 标签（`sprint-0` … `sprint-3`）
- Issue 标题可读，正文含验收要点；缺陷须含：现象、复现、优先级、状态
- 看板（GitHub Projects 或飞书多维表格）中的卡片须能对应到 Sprint 与 OpenSpec task
- 认领任务：Assignee 为自己，进行中再动手改代码

## 5. OpenSpec

- 新能力或行为变更：先在 `openspec/changes/<change-id>/` 建立 proposal → specs → design → tasks
- **禁止**只改代码不更新规格
- 任务勾选完成 ≠ 验收通过；须附运行/测试证据（截图、测试记录或 CI）
- 完成后归档 change，保证 `openspec/specs/` 与产品一致

## 6. 开发与测试（全员）

- 五人全员参与开发；测试贯穿各 Sprint，Sprint 3 为集中验证而非首次测试
- 每人负责本模块：正向验收 + 至少 1 个异常/边界场景
- 后端负责核心业务单测；各端维护主路径冒烟清单
- 合并前：本地冒烟通过，并在 PR 中写明结果

## 7. 周报与沟通

- **每周五**课上简短汇报，并产出工作周报（已完成 / 下一步 / 问题）
- 周报放入 `docs/周报/`，文件名：`YYYY-MM-DD-第N周.md`
- **每周三前**可约甲方（任课教师）15 分钟讨论
- 组内决策（技术选型、范围裁剪）记入 `docs/会议纪要/` 或 Issue 评论

## 8. 目录边界（减少冲突）

| 目录 | 主要修改人 |
|------|------------|
| `backend/` | 后端主责 |
| `android/` | Android 主责（可两人分模块，不同包路径） |
| `web/` | Web 主责 |
| `openspec/`、`docs/` | 过程协调人牵头，全员可改自己相关部分 |

跨模块改动：先开 Issue 对齐接口字段，再并行开发。

## 9. 提交信息

使用简洁中文或英文均可，推荐：

```
feat(android): 完成日志新建页
fix(backend): 修复任务派发权限校验
docs(openspec): 补充日志规格场景
test(backend): 增加日志创建边界单测
```
