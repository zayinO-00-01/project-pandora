# 设计与验证方案

## 基线

代码对照 `main@2fa2104`（Android `0.10.25`）。一期功能由 [一期 OpenSpec](https://github.com/zayinO-00-01/project-pandora/pull/46) 记录。现有任务列表按账号取任务，Android 使用北京时间的截止日期来分组。

## 取数

- 摘要只取网格范围（包括显示的相邻月份日期，最多 42 天）。后端把北京时间的起止日换算成左闭右开的时间范围，先过滤可见任务，再按天统计总数并选前两条。月历只展示自己创建或负责的有效任务；不会把只为审批而开放的临时详情权限扩展到月历。
- 当天列表每页 30 条，按未完成优先、优先级、截止时间、任务 ID 排序。多人责任任务按任务 ID 计一条。数据没有发生变化时，翻页不应漏项或重复。分页期间如有改期或任务状态变化，刷新日历可重取第一页。
- 现有任务接口继续给其他页面使用。公司日历只请求可见日期的摘要和当前选中日期的列表，不借用全量任务接口取数。摘要和列表以账号、日期范围及刷新轮次区分；快速翻月或换账号时丢弃过时响应。
- 改期获批或直接生效后刷新受影响日期。申请仍待审或被驳回时，继续显示旧日期；按任务原有规则查详情、看标签和执行改期。
- V32 给已审批任务的日期范围查询增加索引。CRM 变更占用 V30 和 V31；发布时先应用 CRM 的迁移，或把 V30、V31 和 V32 随同一个后端版本发布，避免低版本迁移被跳过。后端上线后再更新 Android 客户端。

## 怎么判断值得做

后端已用 100、1,000、10,000 条虚构任务对比原全量接口，见 [验证记录](verification.md)。真机还需用同一台设备、同一个测试后端、固定网络和账号记录首屏、翻月和打开当天首批列表的耗时，区分冷启动和连续翻月。摘要条数不得随某天任务总量线性增加，当天剩余条数必须准确。
